# NIST SP 800-207 Zero Trust Architecture Reference

## Core Definition

Zero Trust (ZT) provides a collection of concepts and ideas designed to minimize uncertainty in enforcing accurate, least privilege per-request access decisions in information systems and services in the face of a network viewed as compromised.

Zero Trust Architecture (ZTA) is an enterprise's cybersecurity plan that utilizes zero trust concepts and encompasses component relationships, workflow planning, and access policies.

## Seven Tenets (Mandatory)

### 1. All Data Sources and Computing Services Are Resources
- Includes devices, infrastructure, applications, virtual components, cloud services
- No implicit trust based on network location
- Each resource requires individual protection

### 2. All Communication Is Secured Regardless of Network Location
- Network location (internal/external) does not imply trust
- All traffic encrypted, authenticated, authorized
- Mutual TLS (mTLS) or equivalent for service-to-service

### 3. Access to Individual Enterprise Resources Is Granted on a Per-Session Basis
- Trust evaluated per session, not per connection
- Dynamic policy evaluation at each request
- Short-lived credentials, continuous re-verification

### 4. Access to Resources Is Determined by Dynamic Policy
- Policy based on observable state: identity, device, location, behavior, resource sensitivity
- Policy Engine makes decisions; Policy Administrator configures; PEP enforces
- Behavioral attributes (UEBA) feed policy decisions

### 5. The Enterprise Monitors and Measures Integrity and Security Posture
- Continuous monitoring of all assets
- Asset inventory with real-time posture assessment
- Automated response to posture changes

### 6. All Resource Authentication and Authorization Are Dynamic and Strictly Enforced
- Strict enforcement before access allowed
- Continuous authentication (not just at login)
- PDP/PEP separation of concerns

### 7. The Enterprise Collects Information to Improve Security Posture
- Telemetry from all components feeds analytics
- Machine learning for anomaly detection
- Continuous improvement loop

### Policy Engine (PE)
- **Function**: Ultimate access decision (allow/deny)
- **Inputs**: Policy rules, real-time context (identity, device, threat intel, resource attributes)
- **Output**: Decision + optional obligations (logging, step-up auth)

### Policy Administrator (PA)
- **Function**: Establishes/shuts down communication paths between subject and resource
- **Actions**: Configures PEPs, issues short-lived certificates/tokens
- **Authority**: Delegated from PE

### Policy Enforcement Point (PEP)
- **Function**: Enforces decisions, forwards requests to PE
- **Placement**: Sidecar, gateway, agent, network device
- **Stateless**: No local policy decisions

## Data Flows

### Control Plane
1. Subject → PEP: Request access
2. PEP → PE: Forward request + context
3. PE → PA: Decision + obligations
4. PA → PEP: Configure enforcement (certificates, rules)
5. PEP → Subject: Allow/deny + session establishment

### Data Plane
1. Subject ↔ Resource: Encrypted, authenticated session
2. Continuous: PEP monitors, PE re-evaluates on context change

## Deployment Models

### 1. Device Agent / Gateway
- Agent on device + gateway at network edge
- Best for: Remote access, BYOD, legacy apps

### 2. Enclave-Based
- Micro-segmentation via overlay networks (SDP)
- Best for: Data center, cloud workloads, east-west traffic

### 3. Resource Portal / Application Gateway
- Reverse proxy with integrated PE/PEP
- Best for: Web apps, SaaS, API gateways

### 4. Service Mesh / Sidecar
- Sidecar proxy per workload (Istio, Linkerd, Consul Connect)
- Best for: Kubernetes, microservices, cloud-native

### 5. Cloud-Native / Identity-Aware Proxy
- Cloud provider native (AWS Verified Access, Azure AD App Proxy, GCP IAP)
- Best for: Cloud-first organizations

## Policy Language Requirements

Per NIST 800-207, policy should be:
- **Machine-readable** (not human-only)
- **Version-controlled** (GitOps)
- **Testable** (automated test suites)
- **Auditable** (decision logs with full context)
- **Dynamic** (real-time attribute evaluation)
